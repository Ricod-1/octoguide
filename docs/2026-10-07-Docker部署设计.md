# OctoGuide Docker Compose 部署设计

日期：2026-10-07
状态：已实现并端到端验证（真实 MySQL 执行初始化 SQL + 真实后端启动通过 Flyway 校验 + API 返回种子数据）

## 目标

用一条命令把 OctoGuide（MySQL + Spring Boot 后端 + Vue/Nginx 前端）跑起来，不再依赖本机的
JDK、Maven、Node 与独立安装的 MySQL 服务，同时不在镜像或仓库里写死任何密钥。

## 交付物

| 文件 | 作用 |
| --- | --- |
| `docker-compose.yml` | 编排 db / backend / frontend 三个服务，含健康检查与启动依赖 |
| `.env.example` | 环境变量模板（端口、数据库口令、LLM 配置、功能开关） |
| `db/init/01-schema.sql` | 建表 + 种子数据 + Flyway 基线，容器首次创建数据卷时自动执行 |
| `backend/Dockerfile` | 多阶段构建：Maven 打 jar → JRE 运行 |
| `backend/.dockerignore` | 排除 `target/` 等，缩小构建上下文 |
| `backend/src/main/resources/application-docker.yml` | 容器内专用配置（连 `db` 服务名，全部走环境变量） |
| `frontend/Dockerfile` | 多阶段构建：Node 构建 → Nginx 托管 |
| `frontend/nginx.conf` | 静态资源 + SPA 回退 + `/api` 反向代理（关闭流式缓冲） |
| `frontend/.dockerignore` | 排除 `node_modules/`、`dist/` 等 |

## 架构与端口

```
浏览器 ──▶ frontend (Nginx:80，宿主机 8088)
                │  /api/*  反向代理
                ▼
           backend (Spring Boot:8080，宿主机 127.0.0.1:8080)
                │  JDBC
                ▼
           db (MySQL 8.0:3306，宿主机 127.0.0.1:3307)
```

- 前端 8088：避开后端 8080，避免与本地已有服务冲突。
- MySQL 3307：避开宿主机通常已被占用的 3306。
- 后端与 MySQL 的宿主机端口只绑定 `127.0.0.1`，不对局域网暴露。
- 三个服务在同一自定义网络 `octoguide-net` 内，通过服务名互相访问。

## 启动流程

1. `db` 启动：mysql 镜像创建数据库、业务账号，并按文件名顺序执行 `db/init/*.sql`。
2. `db` 健康检查通过（用业务账号执行真实查询，而非仅判断进程存活）。
3. `backend` 启动：以 `docker` profile 运行，Flyway 校验迁移状态后启动 Tomcat。
4. `backend` 健康检查通过（请求 `/api/status` 返回 200）。
5. `frontend` 启动：Nginx 托管构建产物，`/api` 反代到 `backend`。

依赖顺序通过 `depends_on` + `condition: service_healthy` 保证，避免前端先起时首屏请求 502。

## 关键设计决策

### 1. 初始化 SQL 与 Flyway 的关系

后端用 Flyway 管理表结构（`V1`~`V8`）。容器部署时若两套机制各建一次表，会互相冲突。
本方案的处理：

- `db/init/01-schema.sql` 由 `V1`~`V8` **按顺序原样合并**生成，并在此基础上追加
  `flyway_schema_history` 的**基线记录**，使 Flyway 认为这 8 个迁移「已执行」。
- 因此后端启动时输出 `Successfully validated 8 migrations` 与
  `Schema 'octoguide' is up to date. No migration necessary.`，既不会重复建表，
  也不会重复插入种子数据。
- 脚本中的 `checksum` 由 Flyway 8.5.13 自身的 `ChecksumCalculator` 计算得出，
  而非手工估算。算法为：逐行读取 → 去掉 BOM → 取该行 UTF-8 字节更新 CRC32，
  **不含行尾换行符**。已用 Flyway 内部方法逐条比对确认一致。

> 维护约定：**一旦修改 `V1`~`V8` 任一脚本，必须同步更新 `db/init/01-schema.sql` 及其 checksum**，
> 否则 Flyway 会报 `Migration checksum mismatch`，后端将启动失败。

### 2. Nginx 用 resolver 而非 upstream

`upstream` 块会在 Nginx **启动时**解析域名，若后端尚未就绪，Nginx 直接启动失败并陷入重启循环。
改用 Docker 内置 DNS（`127.0.0.11`）+ 变量形式的 `proxy_pass`，域名在**请求时**解析：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
proxy_pass http://backend:8080$request_uri;
```

变量写法不会自动附加 URI，故显式拼上 `$request_uri`，保证 `/api/chat` 等路径原样转发。

### 3. 流式响应必须关闭缓冲

`/api/chat` 返回 NDJSON 流式响应。Nginx 默认的 `proxy_buffering on` 和 gzip 都会缓冲内容，
导致回答「攒到最后一次性吐出」，丧失流式体验。故在 `/api/` 中显式关闭
`proxy_buffering`、`proxy_request_buffering`、`proxy_cache` 与 `gzip`，
并把 `proxy_read_timeout` 设为 360s（略大于后端 300s 的 emitter 超时）。

### 4. 健康检查不依赖 `curl`

后端基础镜像 `eclipse-temurin:8-jre-jammy` 通常不预装 `curl`，若直接用它做健康检查，
容器会永远处于 unhealthy 并使前端无法启动。故在镜像构建阶段显式安装 `curl` 并清理 apt 缓存。

### 5. 安全

- 以非 root 用户 `octoguide` 运行后端进程。
- 数据库口令、LLM API Key、知识更新令牌全部通过环境变量注入，镜像与仓库中不含真实密钥。
- `.env` 已加入 `.gitignore`，只提交 `.env.example` 模板。

## 使用方式

```powershell
copy .env.example .env   # 修改 MYSQL_ROOT_PASSWORD、OCTOGUIDE_DB_PASSWORD，按需填 LLM Key
docker compose up -d --build
# 浏览器打开 http://localhost:8088
```

常用命令：

```powershell
docker compose logs -f backend   # 看后端日志
docker compose ps                # 看容器与健康状态
docker compose down              # 停止（保留数据）
docker compose down -v           # 停止并删除数据卷（下次启动会重新初始化数据库）
```

## 不在范围内（YAGNI）

- 不引入 CI/CD 与镜像推送流程。
- 不做 HTTPS/证书自动签发（生产需自行在 Nginx 前加一层反向代理或挂载证书）。
- 不做数据库备份定时任务。
- 不改动现有 `start-all.ps1` 本地开发流程。
